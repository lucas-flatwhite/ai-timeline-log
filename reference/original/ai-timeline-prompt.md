# 「생성형 AI 1,405일」을 다시 만든다면 쓸 프롬프트

처음 요청은 이랬습니다.

> chatgpt 처음 나왔을 때부터 2026.10 까지 ai 관련한 주요 타임라인을 구체적으로 구성해주세요. 아래로 스크롤만해도 전체 흐름을 이해할 수 있도록이요. 스크롤 되면서 주요 텍스트 혹은 이미지가 목판화 스타일로 배경에 보였다가 사라지는 표현. ai slop 을 줄이기. 대체적으로 블랙앤화이트 느낌. 처음으로 보여지는 화면은 시각적으로 압도하는 느낌. 스크롤을 내릴 때 해당하는 타임라인이 샥 고정되면서 좀 더 디테일한 내용이 보이고 더 스크롤 하면 그 다음 타임라인으로.

방향은 이미 좋습니다. 원하는 느낌(목판화, 흑백, 압도하는 첫 화면)과 동작(고정 → 디테일 → 다음)이 다 들어 있어요. 다만 **내용의 기준**(무엇을 넣고 뺄지, 얼마나 정확해야 하는지)과 **완성의 기준**(언제 끝났다고 볼지)이 비어 있어서, 그 부분을 모델이 추측으로 채우게 됩니다. 아래 프롬프트는 그 빈칸을 미리 채운 버전입니다.

---

## 프롬프트

```markdown
# 역할과 목표
한국어 개발자·AI 실무자를 위한 스크롤 연표 웹페이지를 만들어 주세요.
주제는 "ChatGPT 공개(2022-11-30)부터 오늘(2026-10-05)까지 생성형 AI가 지나온 길"입니다.
읽는 사람이 스크롤만 내려도 4년의 흐름을 이해하고, 마지막에 "그래서 무엇이 바뀌었는지"를 한 문장으로 말할 수 있어야 합니다.

용도: X(트위터)와 GitHub Pages에 공유할 포트폴리오 겸 콘텐츠. 모바일에서 처음 보는 사람이 많습니다.

# 1단계: 리서치 (만들기 전에 먼저)
- 장면(챕터)을 24~30개 고르세요. 연도별 배분은 대략 2022: 1, 2023: 5, 2024: 6, 2025: 8, 2026: 8.
- 고르는 기준, 우선순위 순:
  1. 이후 흐름을 바꾼 사건 (새 능력, 새 사용 방식, 시장 충격)
  2. 규제·정책·국가 단위 사건
  3. 한국 관련 사건 (예: 하이퍼클로바X, AI 서울 정상회의, AI 기본법 통과·시행, APEC GPU 공급)
  4. 대중 문화 현상 (예: 지브리 열풍)
- 모델 출시만 나열하지 마세요. 모델 출시는 맨 끝 "모델 계보" 표로 따로 모읍니다.
- 학습 시점 이후(특히 2026년)의 사건은 반드시 웹 검색으로 확인하고, 날짜·수치는 1차 출처(회사 발표, 법원 문서, 주요 언론)를 우선하세요.
- 조사·소송이 진행 중인 사건은 "보도 기준"임이 드러나게 쓰고, 신뢰도가 낮은 보도는 넣지 마세요.
- 정치적으로 민감한 사건(국방부 분쟁, 수출통제 등)은 양쪽 입장을 사실대로만 적고 평가하지 마세요.
- 리서치가 끝나면 페이지를 만들기 전에 장면 목록(날짜, 제목, 한 줄 요약)을 먼저 보여 주세요. 제가 빼거나 더할 수 있게요.

# 2단계: 내용 형식
각 장면은 다음 구조를 지킵니다.
- 판 번호(제1판…), 기간(예: 2024.09–10), 분류어 1개
- 제목: 15자 안팎, 사건을 직접 말하는 문장 (비유·말장난 금지)
- 요약: 2문장, 80자 이내
- 세부 항목: 3~4개, 각 [날짜, 50자 이내 문장]. 반드시 숫자나 고유명사가 하나 이상 들어갈 것
- 판에 새길 핵심어 1개: 그 장면을 대표하는 실제 수치나 이름 (예: "-17%", "260,000", "GPT-4", "19일")

연도가 바뀌는 지점에는 연도 요약 판을 넣습니다 (그해의 성격을 한 구절로 + 2문장).
마지막에는 다음을 둡니다.
- 4년을 3개 시기로 나눈 정리 (예: 묻고 답하기 → 생각하고 손쓰기 → 맡기고 통제하기)
- 연구소별 주요 모델 계보 (OpenAI, Anthropic, Google, Meta, DeepSeek, xAI)
- 출처 목록과 기준일

문체: 짧은 평서문, 신문 연표 톤. "놀라운", "혁명적인", "게임 체인저" 같은 형용사, 이모지, 느낌표 금지.

# 3단계: 시각 방향
- 레퍼런스: 오윤의 민중 목판화, 프란스 마세렐·린드 워드의 목판 소설, 동전·지폐의 선 판화(engraving).
- 색: 먹(거의 검정)과 한지(살짝 회색빛 흰색) 두 가지. 강조색 없음.
- 판화 표현은 생성 이미지를 쓰지 말고 코드로 만듭니다:
  canvas에 글자·도형으로 밑그림을 그린 뒤, 밑그림의 어두운 정도에 따라 굵기가 변하는 평행선(가로, 사선, 물결, 동심원)으로 다시 새겨 주세요.
  선 끝은 끌로 판 것처럼 가늘어지고, 중간중간 이가 빠진 듯 끊겨야 합니다.
- 피해야 할 것 (AI 슬롭): 로봇·뇌·회로 이미지, 보라-파랑 그라데이션, 빛나는 효과, 둥근 카드 남발, 이모지 섹션 표시, 모두 가운데 정렬.
- 서체: 제목은 무겁고 각진 한글 디스플레이체(예: Black Han Sans), 본문은 개성 있는 명조(예: Hahmlet), 날짜는 고정폭(예: IBM Plex Mono).

# 4단계: 스크롤 동작
- 첫 화면: 화면 전체를 채우는 먹판. 경과 일수("1,405일")를 거대하게 새기고 뒤로 햇살 문양.
  로딩 직후 선이 한 번 찍히는 연출 1회. 스크롤하면 문양이 천천히 돌고 숫자가 지워집니다.
- 장면: 섹션 진입 시 판화 선이 무작위 순서로 찍혀 나타나고(잉크가 묻는 느낌),
  화면 상단에 닿으면 판이 고정됩니다.
  고정된 동안 설명판의 세부 항목이 하나씩 "먹을 입고"(흐린 회색 → 검정),
  모두 드러난 뒤 조금 더 내리면 고정이 풀리며 판화가 지워지고 다음 장면이 들어옵니다.
- 항상 보이는 표시: 현재 날짜와 판 번호(모바일 상단), 시간 비례 눈금자(데스크톱 오른쪽, 클릭하면 해당 장면으로 이동).
- 애니메이션은 이 세 가지(첫 화면 찍기, 판화 찍기·지우기, 항목 먹 입히기)만. 그 밖의 효과는 넣지 마세요.

# 5단계: 기술 조건
- HTML 한 파일, 빌드 도구·프레임워크 없음. 외부 리소스는 Google Fonts만.
- 390px 폭 휴대폰에서 고정된 설명판이 화면 안에 다 들어와야 합니다.
  안 들어가는 장면은 글자를 줄이고, 그래도 넘치면 그 장면만 고정을 풀어 일반 스크롤로 보여 주세요.
- 가로 스크롤 없음. 아이폰 안전 영역 대응.
- 성능: 판화는 화면 근처 몇 장만 미리 만들고 멀어지면 메모리에서 해제. 스크롤 중 60fps 목표.
- prefers-reduced-motion이면 모든 판화와 항목을 처음부터 완성된 상태로.
- JS가 꺼져도 글 내용은 모두 읽혀야 합니다.

# 완성 기준
- [ ] 모든 날짜·수치가 출처로 확인됨
- [ ] 휴대폰(390×780)과 데스크톱(1440×860)에서 고정 중 설명판이 잘리지 않음
- [ ] 콘솔 에러 없음
- [ ] 스크롤만으로 처음부터 끝까지 볼 때 3~4분 안에 흐름이 읽힘

# 결과물
1. 장면 목록 초안 (확인용)
2. 완성된 페이지 (아티팩트로 공유 가능하게)
3. GitHub 저장소용 묶음: index.html, README.md(구조, 데이터 수정 방법, GitHub Pages 공개 방법), .nojekyll
```

## 왜 이렇게 구성했나

**목적과 독자를 먼저 씁니다.** "한국어 개발자, 모바일, X 공유용"이라고 적으면 모델이 한국 관련 사건 비중, 문장 길이, 모바일 우선 레이아웃을 스스로 판단할 수 있습니다.

**리서치와 제작을 나눕니다.** 사실관계가 페이지의 신뢰를 결정합니다. 장면 목록을 먼저 받아 보면, 디자인 작업이 끝난 뒤 내용을 갈아엎는 일을 막을 수 있습니다. 학습 시점 이후 사건은 검색으로 확인하라고 명시하는 것도 중요합니다.

**"AI 슬롭 줄이기"를 구체적인 금지 목록으로 바꿉니다.** 막연한 요청은 모델마다 다르게 해석합니다. 무엇을 쓰지 말지(로봇 이미지, 그라데이션, 과장 형용사)와 무엇을 대신 쓸지(실제 수치로 만든 판화)를 함께 적어야 결과가 안정됩니다.

**레퍼런스를 고유명사로 줍니다.** "목판화 스타일"보다 "오윤, 마세렐, 선 판화"가 훨씬 좁고 정확한 방향을 줍니다.

**동작을 상태 변화로 설명합니다.** "샥 고정"은 느낌으로는 정확하지만, "진입 → 고정 → 항목 공개 → 해제 → 지움"처럼 단계로 쓰면 구현이 의도에서 벗어나지 않습니다. 애니메이션 개수를 제한하면 과한 연출도 막습니다.

**완성 기준을 체크리스트로 둡니다.** 특히 "휴대폰에서 설명판이 잘리지 않음"은 실제로 이번 작업에서 가장 손이 많이 간 부분이라, 처음부터 조건으로 걸어 두는 편이 좋습니다.

**결과물을 끝까지 적습니다.** 나중에 GitHub에 올릴 생각이라면 처음부터 README와 데이터 구조를 요청해 두면 됩니다.
